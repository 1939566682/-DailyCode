## 项目整体分析
- 对 beacon-cloud 项目进行了全面分析，产出报告 `报告/项目整体分析.md`
- 项目定位：基于 Spring Cloud 微服务架构的分布式短信平台（SMS Gateway Platform）
- 技术栈：Spring Boot 2.3.12 + Spring Cloud Hoxton.SR12 + Spring Cloud Alibaba 2.2.6 + Nacos + RabbitMQ + Redis + MySQL + Elasticsearch + XXL-Job + Netty(CMPP) + Java 8
- 10 个 Maven 子模块：beacon-common(公共), beacon-api(网关:10001), beacon-strategy(策略:18883), beacon-push(推送:18885), beacon-SmsGateway(网关:18886), beacon-cache(缓存:18882), beacon-synchronization(数据同步), beacon-search(搜索:18884), beacon-monitor(监控:18887), beacon-webmaster(管理后台)
- 核心链路：Client → API(校验链) → MQ → Strategy(策略链) → MQ → Push → MQ → SmsGateway(CMPP/Netty) → 运营商
- 设计模式：策略模式+责任链（CheckFilterContext/StrategyFilterContext 动态校验链）、事件驱动(MQ解耦)、雪花算法(ID)、DFA(敏感词)

## 4个页面500错误根因（本轮终于查明）— 字段名不匹配！

### 用户提供的关键日志（4段堆栈）：
1. **ClientBalanceMapper**: `Unknown column 'current_balance' in 'field list'`
   SQL: `select id, client_id, current_balance, ... from client_balance where client_id=?`
2. **CodeLimitMapper**: `Unknown column 'limit_state' in 'field list'`
   SQL: `select id, limit_time, limit_count, description, limit_state, ... from code_limit`
3. **SmsTempMapper**: `Table 'beacon_cloud.sms_temp' doesn't exist`
   SQL: `SELECT count(0) FROM sms_temp`
4. **ClientAccountRecordMapper**: `Unknown column 'paidvalue' in 'field list'`
   SQL: `select id, client_id, paidvalue, paidstate, paidinfo, ... from client_account_record`

### 根因分析
- 4 个 Mapper.xml 是 MBG 自动生成的，对应 Entity 字段（`currentBalance`/`limitState`/`paidvalue` 等）
- 4 个 Entity 是用 `synchronization` 模块原有的，不是按 `new_tables.sql` 重新生成的
- 用户的数据库里这 4 张表的实际列名跟 Entity 字段**不匹配**：
  - `client_balance` 表里**没有** `current_balance` 列
  - `code_limit` 表里**没有** `limit_state` 列
  - `client_account_record` 表里**没有** `paidvalue` 列
  - `sms_temp` 表**整个不存在**
- 这是 3 轮诊断最大的教训：**Entity 和 Mapper 是一体的，但数据库表可能是用户从别处导入的旧表，列名对不上**

### 解决方法（需要用户配合）
**最关键**：用户必须提供这 4 张表的真实 DESC 输出，我才能改 Mapper.xml 和 Entity
- 现在 4 个 Mapper.xml 的列名跟用户实际表的列名不一致
- 我之前写的 `new_tables.sql` 第 11-15 张表（client_business/client_balance/client_account_record/code_limit/sms_temp）是**错的** — 因为用户已经有这些表（只是列名跟我写的不一样），执行了反而冲突

### 待办
- 拿到用户实际表结构后，修改 4 个 Mapper.xml + 4 个 Entity
- 不要执行 new_tables.sql 第 11-15 段

### 教训
- **绝对不能凭 Entity 字段推测数据库表结构**
- **必须先看真实错误日志（DESC 命令）才能动手改**
- 这次 3 轮诊断走了 2 次弯路（先误判"表不存在"、再误判"DDL缺失"），真正的根因是**字段不匹配**
